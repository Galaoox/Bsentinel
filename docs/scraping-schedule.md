# Scraping escalonado (un solo proceso)

## Calendario y selección

Cada relación libro–tienda persiste `scrape_group` (0, 1, 2) y `next_check_at` en UTC. La política efectiva son **dos revisiones diarias** en `America/Bogota`: grupo 0 **08:00/17:00**, grupo 1 **08:20/17:20**, grupo 2 **08:40/17:40**. APScheduler despierta con cron absoluto (horas `8,17`, minutos `0,20,40`, timezone Bogotá), no un intervalo desde el arranque. La tolerancia de **inicio de lote** es menor de 120 segundos del slot (cron misfire grace **119 s**), independiente del plazo de **trabajo de 20 minutos**: grupo 0 [08:00,08:20), grupo 1 [08:20,08:40), grupo 2 [08:40,09:00), y respectivamente [17:00,17:20), [17:20,17:40), [17:40,18:00). Sólo la cohorte de inicio se encola. La admisión se revalida después de lecturas SQL/guard y de esperar el permiso global, e inmediatamente antes de cada intento/retry de transporte. Hasta tres requests iniciados antes del límite pueden terminar después; ningún intento nuevo ni retry comienza al vencer. Startup no ejecuta inmediatamente ni reproduce el cron perdido. `trigger_now` activa un lote periódico sujeto a la tolerancia de inicio, no es una revisión manual de relación. Un trigger forzado del scheduler fuera de ventana no consulta tiendas ni carga candidatos. No se reproducen slots perdidos: un atraso se difiere o usa únicamente la ventana vigente de su propio grupo, nunca otra cohorte.

La migración `0007_add_scraping_schedule`, posterior a `0006_add_panamericana_store`, asigna grupos por `created_at, id` en round-robin. Conserva libros, precios, `last_checked` e historial. Inicializa el primer slot futuro compatible con `last_checked + una hora`. Nuevas relaciones eligen el grupo elegible menos poblado; SQL serializa esa asignación en el proceso hasta commit/rollback. El scrape inicial individual/bulk se conserva y actualiza el calendario usando su timestamp.

La ventana se reserva y confirma **antes de HTTP** con el próximo slot y un incremento de `scrape_generation`. Un crash, cancelación o fallo SQL al publicar no permite repetirla tras reiniciar. Al terminar tarde se avanza al primer slot posterior a finalización y ventana consumida. Fallos CAPTCHA/pausa/transporte conservan precio, estado, último éxito e historial; no fabrican agotado ni precio cero. Restaurar libros, reactivar/restaurar tiendas habilitadas y cambiar una URL reprograma hacia el futuro manteniendo el grupo. La revisión manual explícita y creación inicial siguen permitidas fuera de ventanas (excepto tienda pausada); una manual no consume un slot periódico todavía futuro y aumenta la generación para invalidar snapshots concurrentes.

## Recursos, carreras y apagado

- Tres workers y cola de seis elementos; páginas de hasta 60 candidatos mediante keyset SQL por fecha/ID, con corte temporal fijo.
- Una sola instancia de lote por proceso: guard compartido incluso para llamadas directas; el scheduler añade exclusión automática/manual, `max_instances=1`, `coalesce=True` y descarta activaciones mientras está ocupado (no acumula tareas).
- Un runtime compartido limita a tres fetches de tiendas, incluidos creación individual, importaciones, revisiones periódicas y manuales. No limita OpenLibrary ni todo el tráfico externo.
- HTTP ocurre sin sesión SQL del worker. Snapshot y resultado usan sesiones independientes cortas. La publicación revalida URL/calendario, `scrape_generation` y habilitación de libro/tienda; precio, estado, timestamp e historial se confirman juntos; el calendario ya se reservó de manera independiente antes de HTTP. La generación persistida aumenta al restaurar libros, reactivar/restaurar tiendas o cambiar URLs, aunque el calendario termine en el mismo slot o la URL vuelva a su valor anterior. La migración 0007 inicializa esta generación en cero.
- Toda revisión manual de una relación confirmada, incluso con `last_checked=None`, usa el mismo procesador/lock por relación desde el wiring de la app. Solo las creaciones individual/bulk indican explícitamente `initial=True` y conservan su transacción propia; no se delega una relación todavía no confirmada.
- El cliente Scrapling instalado advierte contra compartir una sesión curl concurrentemente. Cada fetch HTTP tiene su propia `FetcherSession` y cierra su sesión incluso ante excepción/cancelación; el permiso exterior cubre sus reintentos. El manager de arranque conserva validación/lifecycle compatible y no realiza consultas.
- El proxy HTTP configurado se pasa explícitamente en cada `session.get`: Scrapling 0.4.2 puede anular el proxy predeterminado con `None` si se omite. Un fallo de proxy se propaga sin fallback directo. El modo browser con proxy configurado se rechaza al construir el runtime, antes de iniciar navegador o scheduler, hasta implementar soporte de proxy browser.
- Cancelación se propaga; TaskGroup cancela/espera producer y workers. El scheduler cancela/espera sus tareas antes de cerrar runtime, con presupuesto de cinco segundos. Si no terminan, se informa timeout y no se cierra el runtime bajo tareas vivas.

## Configuración

| Variable | Default | Significado |
|---|---:|---|
| `SCHEDULER_SCRAPE_TICK_MINUTES` | 20 (legacy) | Aceptada por compatibilidad; no modifica el cron absoluto. |
| `SCRAPING_BLOCK_COOLDOWN_MINUTES` | 60 | Pausa por tienda tras CAPTCHA/challenge, entero positivo. |
| `SCRAPING_CONCURRENCY` | 3 | Capacidad compartida de fetches, entre 1 y 3. |
| `SCHEDULER_SCRAPE_INTERVAL_HOURS` | 6 (legacy) | Conservada para compatibilidad de configuración; el wiring de la app ya no la usa. |

`stores.scrape_interval_hours` tampoco cambia la política de dos ventanas de este ajuste. Los workers permanecen en tres aunque se reduzca la capacidad de fetches. El límite no aumenta automáticamente.

Los logs registran zona/horas/grupos/capacidad efectiva, conteos seleccionadas/exitosas/fallidas/omitidas/skipped/captcha/blocked/paused, duración, retraso máximo y pico de fetches del proceso. Fallos y omisiones usan ID y tipo/motivo, sin URL, texto SQL ni diagnósticos potencialmente sensibles.

## Pruebas y operación

Las pruebas nuevas cubren calendario, migración/backfill/downgrade, due SQL/in-memory, aislamiento transaccional, revalidación en vuelo, carrera manual, cancelaciones, scheduler y carga de 303 relaciones ficticias con errores HTTP/SQL y consultas adicionales concurrentes. La fixture SQL usa SQLite temporal; puede usar PostgreSQL **desechable** mediante `SCHEDULE_TEST_POSTGRES_URL` (solo `127.0.0.1`, puerto diferente de 5432 y DB `bsentinel_schedule_test`, schemas únicos). Nunca apuntar esta variable a un servicio existente: esas restricciones no reemplazan la comprobación de que el contenedor es de prueba.

**Restricciones:** requiere una única réplica/proceso con scheduler. No hay Redis/Celery ni coordinación distribuida. Los grupos equilibran cantidad, no costo. Caídas no generan catch-up fuera de ventanas; se conserva el límite y se descartan slots perdidos. Hasta tres requests ya admitidos pueden completar tras abrirse la pausa de una tienda. Respetar las restricciones y reevaluar el ritmo ante 429. La regresión con 60 relaciones SQL por cohorte y reloj progresivo de 10 s por inicio (modelo agregado de tres workers con requests de 30 s) revisa las 60 en ambas franjas; no es un benchmark merchant. Un catálogo cuyo trabajo exceda 20 minutos puede dejar cola sin revisar; no se garantiza capacidad ilimitada ni equidad/rotación para ese exceso. Medir skipped y tiempos antes de ampliar catálogo. Estas pruebas no miden rendimiento de tiendas ni CPU/RAM productivos.

Este cambio es código/test; no despliega. El responsable de despliegue debe respaldar DB, aplicar la migración una vez en ventana controlada y verificar rotación automática/recurrencia y recursos. Para rollback de app conservar la migración aditiva; no ejecutar downgrade productivo.

## Detector y circuito por tienda

`x-amzn-waf-action` y su valor se comparan sin distinguir mayúsculas: `captcha` → `captcha_blocked`, `challenge` → `challenge_blocked`. Se clasifican **antes** del HTTP >=400 y del extractor. El fallback exige título HTML `Human Verification` **junto con** un script AWS WAF (`*.awswaf.com/.../challenge.js` o `captcha.js`); texto de un producto que simplemente menciona CAPTCHA no bloquea. Un 405 sin señales continúa siendo `http_error`; 202 sin señales explícitas conserva los retries transitorios preexistentes.

El runtime obtiene primero uno de los tres permisos globales y luego verifica el guard compartido de la tienda. Publica la pausa antes de liberar el permiso. Cada intento de red interno revalida la pausa/ventana; errores de admisión tipados no entran al retry de curl. No hay retry de extractor ante CAPTCHA. Requests admitidos previamente (máximo tres) pueden completar; queued/manual/catalog posteriores no envían. Otras tiendas continúan. Los intentos recibidos conservan status 405 y contadores reales; una omisión sin HTTP no crea evento cero-byte.

`StoreGuard` escribe en `scraping_store_blocks(store_id,blocked_until,reason)` mediante sesiones independientes cortas, con upsert condicional que conserva el mayor `blocked_until`. No se modifica `stores.is_active` ni se detiene servicio/container. Creación individual y bulk no pueden deshacer este estado al revertir su transacción. Al vencer, un único probe HALF-OPEN por tienda/proceso permite comprobar recuperación; otros entrantes mientras el probe vive fallan rápido. Sólo una respuesta usable limpia el estado observado con compare-and-delete; un éxito anterior no limpia una pausa más reciente. Fallo de probe renueva el cooldown. Locks referenciados se eliminan cuando no tienen usuarios. Con backend in-memory la pausa no sobrevive al proceso; la garantía durable requiere SQL. Múltiples procesos no coordinan el probe entre sí: se mantiene la restricción de una única réplica/proceso.

API compatible: errores de CAPTCHA/challenge/pausa son HTTP **400**, código `SCRAPING_ERROR`, `details.scraping_reason` específico. Pausa incluye `store_id`, dominio, razón y `blocked_until` UTC, sin URL ni credenciales en los nuevos logs/diagnósticos. Una revisión manual fallida preserva datos y propaga este error. La pausa no promete éxito automático al vencer ni atribuye el bloqueo al proxy/IP.

4. Arrancar una sola réplica/proceso y leer logs: timezone Bogotá, horas 8/17, cohortes 0/20/40, concurrencia <=3, cooldown 60 (o configurado). `/health` sólo verifica lifecycle, no tienda. Restaurar DB sólo con autorización y considerando cambios posteriores al backup.
